# DeepSeek-V3.2 完整模型预填充性能实验计划

本文档给出 [Issue #170](https://github.com/vllm-project/afd-plugin/issues/170)
后续性能实验的完整方案。实验目标不是预设 Attention–FFN 解耦一定更快，
而是在完整模型、自然专家路由和相同硬件资源下，回答以下问题：

1. 32 卡 `16 Attention + 16 FFN` 部署是否有收益；如果没有，瓶颈在哪里？
2. 增加 Attention 资源以后，64 卡 `48 Attention + 16 FFN` 部署能否超过
   64 卡传统部署？
3. 异步流水、token 均分、专家通信和资源切分分别贡献了什么？
4. 收益是在空载延迟、尾延迟还是满足延迟目标时的最大吞吐上体现？
5. 在哪些负载和请求长度分布下没有收益，甚至出现回退？

本文档同时规定公平性规则、运行顺序、停止条件、数据产物和报告口径。
任何未在本文档中列为正式实验的旧结果、调试结果或性能追踪结果，都不能
直接用于最终性能结论。

## 1. 一页摘要

### 1.1 固定不变的实验条件

- 模型：完整 61 层 DeepSeek-V3.2 W8A8，即权重和激活都使用 8 位量化，
  不使用裁剪模型。
- 专家路由：使用模型产生的自然路由，不强制均衡专家编号。
- 专家负载均衡器：关闭 EPLB，不在运行期间迁移或复制专家。
- 执行模式：传统部署和 Attention–FFN 解耦部署都使用 eager 模式。
- 上游双批重叠：传统部署不启用，因为当前上游版本尚未支持该路径。
- 前缀缓存：关闭。
- 输出长度：1 token，使实验集中测量预填充阶段。
- 预填充 MC2：关闭。52K～64K 单步预填充不使用按共同批上限预留的大型
  MC2 工作区。
- 最大模型长度：两边统一设为 70,000，覆盖数据集中 63,778 token 的最长
  输入及输出 token。
- 单个 Attention 数据副本的最大并发请求数：两边统一设为 8。
- 最大批处理 token 数：两边完全相同；优先使用 65,536，任一系统不稳定时
  两边统一降为 32,768。
- 数据集：[`ShwStone/moonconv-wildchat-prefill`](https://huggingface.co/datasets/ShwStone/moonconv-wildchat-prefill)，
  固定 revision `d7d54c16db9d4b2348729b4170a9612b8a47b64a` 和 bundle
  `fe4f751b6dab`。
- 到达过程：使用数据集内冻结的 Mooncake-derived 基础到达偏移，并按统一的
  目标输入 token/s 生成缩放计划；不再生成 Poisson 到达。
- 正式工作负载：`formal_0`、`formal_1`、`formal_2` 三个互不重叠的窗口，
  每个窗口 512 条请求，正式输入共 15,803,063 token。
- 主要服务目标：请求零失败，首 token 延迟的第 99 百分位不超过 10 秒。

### 1.2 两组正式资源对等比较

| 总卡数 | 传统部署 | Attention–FFN 解耦部署 | 目的 |
|---:|---|---|---|
| 32 | 4 个 Attention 数据副本，每个副本使用 8 卡张量并行；32 卡专家并行 | 16 卡 Attention，16 卡 FFN | 测量受 FFN 权重容量限制的最小完整模型拓扑 |
| 64 | 8 个 Attention 数据副本，每个副本使用 8 卡张量并行；64 卡专家并行 | 48 卡 Attention，16 卡 FFN | 测量更合理的 Attention/FFN 资源比例是否产生等卡收益 |

32 卡结果允许为负。`16 Attention + 16 FFN` 是由完整模型至少需要 16 张
FFN 卡这一容量条件产生的拓扑，不应预设它是性能最优拓扑。

### 1.3 实验分为四步

1. **数据与性能追踪冒烟检查**：确认 token ID、长输入、开放环到达和性能
   时间线都能按计划工作。
2. **32 卡机制实验**：比较无双批流水、按请求拆分和按 token 拆分，确定收益
   来源和 Attention/FFN 阶段比例。
3. **32 卡资源对等实验**：测量传统 32 卡部署与 `16 Attention + 16 FFN`
   的实际容量差异。
4. **64 卡周末实验**：在约 8 小时资源窗口内比较传统 64 卡部署与
   `48 Attention + 16 FFN`。

只有正式、无性能追踪插桩、完整工作负载的结果才能用于核心性能数字。

## 2. 术语和部署结构

### 2.1 模型执行阶段

一次 DeepSeek-V3.2 层计算可以简化为两个主要阶段：

1. **Attention 阶段**：完成注意力、归一化、路由计算以及该角色保留的其他
   稠密计算。
2. **Feed-Forward Network 阶段**：以下简称 FFN，接收路由后的 token，执行
   Mixture-of-Experts 专家计算，再把结果返回给 Attention。

**Attention–FFN Disaggregation** 是把这两个阶段放到不同设备进程上运行。
本文简称为“Attention–FFN 解耦”，必要时使用项目名称 AFD。

CAM 是本项目所使用的 Ascend 跨角色通信运行时名称。本文不对 CAM 字母作
未经确认的英文展开，只把它理解为 Attention 与 FFN 之间执行 token 分发和
结果合并通信的组件。

### 2.2 并行方式

| 名称 | 英文及缩写 | 本文中的含义 |
|---|---|---|
| 数据并行 | Data Parallelism，DP | 多个 Attention 副本分别处理请求。例如 DP4 表示 4 个数据副本。 |
| 张量并行 | Tensor Parallelism，TP | 一个 Attention 副本内由多张卡共同计算。例如 TP8 表示每个副本使用 8 张卡。 |
| 序列并行 | Sequence Parallelism，SP | 在张量并行组内切分 token 序列；当前 Attention 路径使用 Ascend 的 FlashComm1 序列并行实现。 |
| 专家并行 | Expert Parallelism，EP | 把 Mixture-of-Experts 的专家权重分散到多张卡。例如 EP32 表示专家分布在 32 张卡上。 |

`DP4 × TP8` 因此表示 4 个数据副本，每个副本使用 8 张卡，总计 32 张卡。

### 2.3 三种 Attention–FFN 解耦模式

| 名称 | 完整描述 | 用途 |
|---|---|---|
| A0 | 不启用异步混合专家双批流水；整个批次作为一个阶段运行 | 测量角色拆分、EP16 和 CAM 通信本身的成本或收益 |
| A1 | 启用两个阶段，在请求边界把批次分成两部分 | 测量双阶段流水收益；长短请求混合时可能失衡 |
| A2 | 启用两个阶段，按实际 token 数把批次分成两部分 | 生产候选；测量 token 均分能否改善长短请求混合场景 |

这里的“两阶段”不是指模型只有两层，而是把同一个调度批次分成两个更小的
子批次。Attention 处理第二个子批次时，FFN 可以处理第一个子批次，从而
形成流水。

### 2.4 性能指标

| 名称 | 英文及缩写 | 定义 |
|---|---|---|
| 首 token 延迟 | Time to First Token，TTFT | 客户端发出请求到收到第一个输出 token 的时间，包含排队和预填充计算。 |
| 服务目标 | Service Level Objective，SLO | 本实验要求 TTFT 第 99 百分位不超过 10 秒，且请求零失败。 |
| 请求速率 | Requests per Second，RPS | 客户端每秒发出的平均请求数。 |
| 有效输入吞吐 | goodput | 在满足 SLO 的前提下，每秒成功处理的输入 token 数。 |
| 最大批处理 token 数 | max-num-batched-tokens，本文称共同批上限 | 单个 Attention 数据副本在一个调度步骤中最多处理的 token 数。 |
| 性能追踪 | profiler | 记录算子和通信时间线。性能追踪会引入开销，因此只用于解释机制。 |
| 性能时间线 | trace | 性能追踪器导出的算子、通信和等待事件记录。 |
| 预热 | warmup | 正式计时前先运行少量请求，使模型加载、内存分配和算子初始化完成。 |
| 无插桩运行 | clean run | 关闭性能追踪和调试插桩的运行；正式性能数字只能来自这种运行。 |
| 筛选运行 | screening run | 使用较短工作负载快速寻找容量区间，不直接提供最终容量结论。 |
| 运行清单 | manifest | 随每次运行保存的配置、版本、数据校验值和有效性信息。 |
| 设备进程编号 | rank | 分布式运行中每个设备进程的唯一编号。 |
| SHA-256 校验值 | SHA256 | 文件内容的摘要；内容变化时校验值也会变化，用于确认两次运行使用相同数据。 |
| eager 模式 | eager execution | 每次运行直接执行算子，不使用预先捕获的计算图；本文两个系统都采用该模式。 |
| 前缀缓存 | prefix caching | 复用相同输入前缀的已计算结果；本文关闭该功能，避免缓存命中改变预填充工作量。 |
| 分块预填充 | chunked prefill | 当一个长输入超过单步 token 上限时，分多个调度步骤完成预填充。 |
| 双批重叠 | Dual Batch Overlap | 上游把一个批次拆为两个子批次并重叠执行的能力；当前传统基线不启用。 |
| 基础到达偏移 | base arrival offset | 数据集中相对窗口第一条请求的到达时间；同一时间戳的请求保持同时到达。 |
| 时间膨胀系数 | dilation factor | 对基础到达偏移做统一缩放的系数；大于 1 降低负载，小于 1 提高负载。 |
| 拓扑简写 | 例如 16A16F | A 表示 Attention 卡数，F 表示 FFN 卡数；16A16F 即 16 张 Attention 卡加 16 张 FFN 卡。 |
| CANN | Compute Architecture for Neural Networks | Ascend 软件栈和算子运行环境。 |
| K | 1,024 | 本文的 8K、24K、32K、64K 分别表示约 8,192、24,576、32,768、65,536 token。 |
| 开放环负载 | open-loop load | 客户端按预定时间发送请求，不因服务器变慢而主动降低发送速率，因此能观察排队和过载。 |

## 3. 为什么 16 Attention + 16 FFN 未必有收益

### 3.1 FFN 至少需要 16 张卡

完整模型有 61 层，其中前 3 层是稠密层，后 58 层包含 256 个路由专家。
模型隐藏维度为 7,168，单个专家中间维度为 2,048。忽略小量偏置和
量化元数据，一个专家的主要参数量约为：

```text
3 × 7,168 × 2,048 ≈ 4,404 万参数
```

58 层路由专家权重平均分到 FFN 设备进程后：

| FFN 专家并行规模 | 每张卡的路由专家权重 | 加一个共享专家后的近似权重 | 结论 |
|---:|---:|---:|---|
| 16 | 约 40.9 GB | 约 43.4 GB | 可以继续为运行缓冲、量化元数据和通信空间留出显存 |
| 8 | 约 81.8 GB | 约 84.3 GB | 权重本身已经超过 64 GB，完整模型不可行 |

因此，32 卡 Attention–FFN 解耦部署最多只能给 Attention 留出 16 张卡。
`24 Attention + 8 FFN` 只适用于之前的 10 层裁剪实验，不能承载完整模型。

### 3.2 资源守恒给出的上界

设每个 token 的 Attention 工作量为 `A`，FFN 工作量为 `F`。如果 32 张卡
都能理想线性扩展，传统部署的理想吞吐与下面的量成正比：

```text
32 / (A + F)
```

16 张卡执行 Attention、16 张卡执行 FFN 时，流水吞吐由较慢阶段决定：

```text
min(16 / A, 16 / F)
```

两者的理想吞吐比为：

```text
(A + F) / (2 × max(A, F))，该值不会大于 1
```

这说明“拆分并重叠”本身不会凭空增加算力。Attention–FFN 解耦只有在修复
传统部署的实际低效时才可能获胜，例如：

- EP32 跨节点专家通信效率低；
- EP32 每张卡收到的 token 太少，专家矩阵乘过小；
- 自然路由造成慢设备进程，其他设备进程被迫等待；
- 两阶段流水隐藏了 FFN 和通信时间；
- 较少的 Attention 数据副本使每个副本更容易形成有效 batch；
- 角色拆分释放显存，使系统能使用更大的共同批上限。

如果这些收益不足以抵消 Attention 卡数减半和新增 CAM 通信，16A16F 就会
回退。该结果是有价值的容量边界，不应隐藏。

## 4. 需要验证的假设

### 4.1 假设一：16A16F 的主要瓶颈是 Attention 资源不足

**支持证据：**

- Attention 持续繁忙；
- FFN 有明显空闲；
- Attention 等待 FFN 的时间较少；
- 把 Attention 从 16 卡增加到 48 卡后，吞吐明显提高。

**反对证据：**

- FFN 或 CAM 通信占据关键路径；
- Attention 大量等待 FFN；
- 增加 Attention 卡数没有明显改善。

### 4.2 假设二：EP16 的通信局部性和计算粒度优于 EP32/EP64

传统 32 卡部署的专家并行跨越 32 张卡。Attention–FFN 解耦部署把专家限制
在 16 张 FFN 卡上。可能的收益包括更小的通信域、每个设备进程收到更多 token，
以及更大的分组矩阵乘计算批次。

**需要观察：** FFN 算子时间、分发/合并通信时间、每个 FFN 设备进程的
token 数、最慢设备进程与平均设备进程的差异。

### 4.3 假设三：A2 能隐藏 FFN 和通信时间

在总 token 数相同的均衡工作负载上比较 A0 与 A2。如果 A2 更快，且
性能时间线中 Attention 与 FFN 确实有时间重叠，才能把收益归因于双阶段流水。

仅凭示意图或客户端平均延迟不能证明计算重叠已经发生。

### 4.4 假设四：token 均分只在请求长度偏斜时有额外价值

- 请求长度接近时，A1 和 A2 应当接近；
- 一个很长请求与多个短请求混合时，A1 无法拆开长请求，A2 应明显更平衡；
- 如果均衡工作负载中 A2 也远快于 A1，需要从 token 填充、调度或实现
  差异继续解释，不能直接归因于 token balance。

### 4.5 假设五：主要收益体现为满足延迟目标时的容量，而非空载延迟

AFD 增加了跨角色通信。低负载时没有排队，额外通信可能使单请求更慢；负载
升高后，流水和专家效率可能减缓排队增长。因此主指标采用满足服务目标的最大
有效输入吞吐，同时报告共同负载下的首 token 延迟。

## 5. 公平性和可复现性规则

### 5.1 必须相同的配置

一次对照中的两个系统必须保持以下项目相同：

- 模型权重文件和分词器；
- vLLM、vLLM Ascend、AFD Plugin、CANN 和容器版本；
- W8A8 量化配置；
- eager 模式；
- 最大模型长度；
- 共同批上限；
- 最大并发请求数；
- 前缀缓存关闭；
- 输出长度 1；
- 数据集 revision、bundle ID、请求文件和到达文件；
- 输入数据、请求顺序和缩放后的到达时间；
- 自然专家路由；
- EPLB 关闭；
- 请求超时和失败判定；
- 测量窗口和预热规则。

设备内存利用率等角色相关配置使用已经通过完整模型正确性验证的启动值，并在
第一次正式运行前冻结。它们不作为性能调优变量，也不能在重复之间改变。

传统部署不启用上游双批重叠。AFD A2 是本项目自身的异步混合专家双阶段
流水，不能把它描述为上游双批重叠。

### 5.2 共同批上限

正式对照优先使用 65,536 token。数据集最长输入为 63,778 token，因此该值
允许每条请求单独在一个调度步骤中完成预填充。一次突发中多条请求的总 token
数仍可能超过共同批上限，此时调度器可以正常分批，不能截断请求。

如果任一系统在该设置下出现启动失败、显存不足或持续不稳定：

1. 两个系统都统一降为 32,768；
2. 确认两个系统使用完全相同的分块预填充设置；
3. 确认所有长请求都被完整处理，没有截断或静默跳过；
4. 如果当前 AFD 路径无法在 32,768 下正确处理最长请求，则停止正式实验，
   不能通过裁剪数据集来制造可比较结果。

不允许分别为传统部署和 AFD 选择不同的共同批上限。

### 5.3 正式数据与诊断数据分离

- 开启性能追踪、形状日志、算子输入输出日志或强制均衡路由的运行都是诊断
  运行，不能提供正式吞吐数字。
- 正式性能运行必须关闭上述插桩。
- 诊断运行和正式运行放入不同目录，并在运行清单中标明用途。
- 不得用性能追踪运行的延迟替代无插桩运行的延迟。

### 5.4 不使用旧裁剪实验作为正式证据

当前分支中的旧实验使用 10 层裁剪模型、强制均衡路由和 `24 Attention +
8 FFN` 拓扑。它可以帮助提出假设和选择初始点，但不能与本实验混合统计，
也不能把其中的加速比写入完整模型最终结论。

## 6. 工作负载

### 6.1 固定数据版本和边界

正式实验只使用以下不可变数据版本：

| 项目 | 固定值 |
|---|---|
| 数据集仓库 | `ShwStone/moonconv-wildchat-prefill` |
| 仓库 revision | `d7d54c16db9d4b2348729b4170a9612b8a47b64a` |
| bundle ID | `fe4f751b6dab` |
| 数据状态 | `data_valid` |
| 服务集成状态 | `not_run_requires_npu_service`，必须在阶段零补齐 |
| DeepSeek-V3.2 tokenizer revision | `a7e62ac04ecb2c0a54d736dc46601c5606cf10a6` |
| 输出长度 | 每条请求 1 token |

在测试服务器上下载整个小型仓库并校验，不通过 `main` 浮动引用：

```bash
hf download ShwStone/moonconv-wildchat-prefill \
  --repo-type dataset \
  --revision d7d54c16db9d4b2348729b4170a9612b8a47b64a \
  --local-dir /data/moonconv-wildchat-prefill
cd /data/moonconv-wildchat-prefill
sha256sum -c SHA256SUMS
```

请求正文已经物化为 `prompt_token_ids`。客户端必须直接发送这些 token ID，
不能 decode 后重新套聊天模板，也不能在运行时重新 tokenize。这样才能保证
`input_length`、内容和不同系统之间完全一致。

数据集由公开 Mooncake FAST'25 Conversation trace 的到达形状和目标长度，
以及公开 WildChat-4.8M 的自然对话前缀构成。它应称为
“Mooncake-derived WildChat prefill workload”，不能称为 Mooncake 原始请求
正文或完整生产流量。

### 6.2 数据集组成

| 窗口 | 请求数 | 输入 token 总数 | 基础时长 | 输入长度中位数 | 第 95 百分位 | 最大值 | 用途 |
|---|---:|---:|---:|---:|---:|---:|---|
| `warmup` | 32 | 331,133 | 无到达计划 | 由短到长分位点覆盖 | — | 47,536 | 启动后预热和服务集成检查 |
| `screening` | 128 | 1,340,915 | 33.000 秒 | 6,702.5 | 32,629.15 | 63,417 | 快速寻找容量区间 |
| `formal_0` | 512 | 5,331,020 | 156.000 秒 | 6,538.5 | 32,313.15 | 63,007 | 正式重复 0 |
| `formal_1` | 512 | 5,260,666 | 150.001 秒 | 6,612 | 31,428.15 | 63,778 | 正式重复 1 |
| `formal_2` | 512 | 5,211,377 | 150.000 秒 | 5,970 | 32,656.25 | 63,649 | 正式重复 2 |

三个正式窗口共 1,536 条请求和 15,803,063 个输入 token，来自 Mooncake
trace 的三个不重叠区域。整个 bundle 共 1,696 条请求和 17,475,111 个输入
token；每条请求对应不同的 WildChat conversation。

数据质量报告记录：输入长度范围为 891～63,778，长度匹配相对误差中位数为
0，第 95 百分位为 0.008135%，所有 CPU 侧来源、内容、长度、到达和可复现性
检查均已通过。NPU 服务重放尚未由数据发布过程验证，因此不能跳过阶段零。

### 6.3 机制实验的固定批次

机制批次只从 `screening` 请求中确定性选择，使机制和容量实验共享同一数据
来源。选择程序按与目标长度的绝对差排序，再按 `request_id` 排序打破平局，
同一请求只使用一次。结果写入 `mechanism_batches.json` 并冻结其 SHA-256。

| 名称 | 选择目标 | 预计总 token 数 | 目的 |
|---|---|---:|---|
| 8K 均衡批次 | 8 条最接近 1,024 token 的请求 | 约 8,192 | 观察小批次下拆分和通信开销 |
| 32K 均衡批次 | 8 条最接近 4,096 token 的请求 | 约 32,768 | 观察两个阶段都能充分工作时的流水收益 |
| 32K 长短混合批次 | 1 条最接近 24,576 token，加 7 条最接近 1,170 token | 约 32,766 | 对比按请求拆分和按 token 拆分 |

所有系统使用同一批 request ID，并把机制批次固定发送到同一个 Attention 数据
副本，避免 DP4、DP2 等不同数据并行规模改变本地批次。每个批次先预热，再做
10 次无插桩重复；性能追踪只抓取 3～5 个有效调度步骤。

三个机制批次都不得超过单个 Attention 数据副本的 8 请求并发上限。客户端应
并发提交一个批次内的全部请求，并确认服务端将它们接收到同一个指定副本；
`DP0` 可以作为约定的固定副本，但不是实验定义的一部分。传统部署和 AFD 必须
使用相同的固定副本规则以及 `--max-num-seqs 8`，不能通过让 16 条请求分两轮
调度来近似一个 32K 固定批次。

如果已经按照旧的 16 条均衡请求或 9 条长短混合请求生成过
`mechanism_batches.json`，该文件及其 SHA-256 必须作废并按上表重新生成；旧批次
产生的阶段一结果不能与新批次结果混合使用。

### 6.4 正式容量工作负载

- 容量搜索只使用独立的 128 请求 `screening` 连续窗口，不从正式窗口抽样；
- 正式点依次使用 `formal_0`、`formal_1`、`formal_2`，作为三组成对重复；
- `warmup` 不计入任何正式指标；
- 正式容量实验使用系统正常的请求分发，不固定 Attention 数据副本；
- 两个系统使用同一种客户端和代理策略，并记录每个数据副本实际收到的请求数
  和输入 token 数。

### 6.5 到达计划和负载缩放

基础 arrival 文件保留 Mooncake trace 的请求顺序、时间差和同时到达关系。
三个正式窗口约 90% 的相邻请求为零时间差，这些突发是工作负载的一部分，
不能加入随机抖动，也不能由同步客户端串行发送。

容量搜索以目标输入 token 到达速率 `R` 为控制量，而不是以请求速率为主控制量。
对于一个窗口：

```text
基础输入 token 速率 = 窗口总输入 token / 基础到达计划时长
时间膨胀系数 d = 基础输入 token 速率 / 目标输入 token 速率 R
缩放后到达偏移 = 基础到达偏移 × d
```

每个窗口根据自身 token 总量计算 `d`，使不同正式窗口在同一实验点具有相同的
目标输入 token/s；传统部署与 AFD 对同一窗口必须读取同一个缩放后计划。
缩放结果一次性换算为整数纳秒并取最近整数，不能由客户端在发送时重复做浮点
计算。每个计划保存：目标 token/s、`d` 的十进制定点字符串、基础 arrival
SHA-256、缩放后 SHA-256、总时长、目标 RPS 和目标 token/s。

客户端必须开放环发送：按绝对偏移调度，同一时间戳的请求并发提交，不等待前一
请求完成。每条请求记录计划发送时间、实际发送时间和发送偏差。若发送偏差第
99 百分位超过 50 毫秒或最大值超过 250 毫秒，说明客户端没有实现计划负载，
该次运行无效。

## 7. 实验拓扑

### 7.1 32 卡传统部署

- 总卡数：32；
- Attention：4 个数据并行副本；
- 每个 Attention 副本：8 卡张量并行和序列并行；
- 专家：跨全部 32 卡做专家并行；
- 记法：`DP4 × TP8，EP32`；
- 模式：eager，无上游双批重叠。

### 7.2 32 卡 Attention–FFN 解耦部署

- 总卡数：32；
- Attention：16 卡，即 2 个数据并行副本，每个副本 8 卡张量并行；
- FFN：16 卡专家并行；
- 记法：`16 Attention + 16 FFN`；
- 正式模式：A2，按 token 拆分；
- 诊断模式：A0、A1、A2。

### 7.3 64 卡传统部署

- 总卡数：64；
- Attention：8 个数据并行副本；
- 每个 Attention 副本：8 卡张量并行和序列并行；
- 专家：跨全部 64 卡做专家并行；
- 记法：`DP8 × TP8，EP64`；
- 模式：eager，无上游双批重叠。

### 7.4 64 卡 Attention–FFN 解耦部署

- 总卡数：64；
- Attention：48 卡，即 6 个数据并行副本，每个副本 8 卡张量并行；
- FFN：16 卡专家并行；
- 记法：`48 Attention + 16 FFN`；
- 正式模式：A2，按 token 拆分。

所有节点应属于相同硬件代际和高速互联域。部署应尽量以整节点划分角色，
FFN 的 16 张卡放在同一个节点，避免把节点内/节点间通信差异混入重复之间。

### 7.5 不进入默认矩阵的拓扑

- `32 Attention + 16 FFN`：总计 48 卡，只在 32 卡性能追踪推断它接近平衡点
  时作为缩放诊断；它没有同样自然的 48 卡传统等资源对照，不作为核心结论。
- `64 Attention + 16 FFN`：总计 80 卡，留待 64 卡实验完成后决定，不进入
  当前 8 小时窗口的默认计划。

## 8. 阶段零：开跑前验收

阶段零只验证实验工具和环境，不产生性能结论。

### 8.1 配置验收

- 从固定 revision 下载数据集，运行 `sha256sum -c SHA256SUMS`，并确认
  `bundle_manifest.json` 的 bundle ID 为 `fe4f751b6dab`；
- 完整模型显示 `num_hidden_layers=61`；
- 自然路由开关已启用，强制均衡开关关闭；
- EPLB 关闭；
- 两边都是 eager；
- `enable_prefill_mc2` 关闭；
- 前缀缓存关闭；
- 模型长度和共同批上限一致；
- 输出长度为 1；
- Attention、FFN 和客户端时间同步状态被记录；
- 32 个或 64 个设备进程全部健康；
- 实际可见设备数与计划一致。

### 8.2 数据和长输入服务验收

数据发布时没有运行 NPU 服务集成测试，因此第一次正式测量前必须完成：

1. 从 `warmup_requests.jsonl` 选取覆盖短、中、长输入的 8 条请求，直接发送
   `prompt_token_ids`，确认服务端接收 token 数与文件完全一致；
2. 运行完整 32 条 `warmup`，确认全部成功且每条输出 1 token；
3. 依次重放接近 32K、52K 和全数据最长 63,778 token 的单请求，记录每卡
   峰值显存；
4. 在 32 卡传统部署上同时向四个 DP 副本各发送一条约 52K 请求，确认 EP32
   在所有数据副本活跃时不会因 MoE 工作区溢出；
5. 检查请求文件与结果中的 request ID、输入长度和顺序能够一一对应。

这些运行只判断可运行性，不提供性能数字。若 65,536 共同批上限在上述长输入
检查中显存不足，按 5.2 节统一评估 32,768 分块预填充，不能只降低某一系统的
配置。

### 8.3 性能追踪冒烟检查

使用 32 卡 `16 Attention + 16 FFN`、A2 和 8K 均衡固定批次：

1. 预热后只追踪 3～5 个有效调度步骤；
2. 确认 Attention 和 FFN 两侧都生成性能时间线；
3. 确认能够识别 Attention 计算、CAM 分发、FFN 计算、CAM 合并和
   Attention 等待；
4. 确认性能时间线包含模型层和阶段的可对齐信息，或能按执行顺序可靠对齐；
5. 检查性能时间线大小，避免正式性能追踪填满磁盘；
6. 用一个已知批次手工核对解析结果。

当前归档包含性能追踪开关，但旧计划提到的性能时间线自动解析脚本未归档。
正式性能追踪前应先根据实际时间线恢复最小解析能力。解析工具只需输出本文
所列指标，不需要恢复旧实验中的全部图表和调试日志。

### 8.4 阶段零通过条件

以下条件全部满足才能进入后续实验：

- 两个正式拓扑均能处理一条完整请求；
- 最长请求和四个 DP 副本并发长请求通过显存检查；
- 客户端能够直接重放 token ID 和冻结到达计划；
- AFD A0/A1/A2 均能在预定固定批次上运行；
- 客户端能固定请求到指定 Attention 数据副本；
- 性能追踪能提供阶段时间；
- 无插桩模式确认没有性能追踪开销；
- 请求计数、token 计数和失败计数一致。

## 9. 阶段一：32 卡机制实验

### 9.1 无插桩固定批次矩阵

| 系统/模式 | 8K 均衡批次 | 32K 均衡批次 | 32K 长短混合批次 |
|---|---:|---:|---:|
| 传统 32 卡部署 | 运行 | 运行 | 运行 |
| AFD A0，无双阶段流水 | 运行 | 运行 | 不必运行 |
| AFD A1，按请求拆分 | 不必运行 | 运行 | 运行 |
| AFD A2，按 token 拆分 | 运行 | 运行 | 运行 |

为减少完整模型启动次数，同一种系统/模式启动一次后依次运行多个固定批次。
每个固定批次先预热，再记录 10 个重复批次。

### 9.2 必选性能追踪重放

| 性能追踪编号 | 配置 | 工作负载 | 回答的问题 |
|---:|---|---|---|
| 1 | 传统 32 卡部署 | 32K 均衡批次 | 传统 Attention、混合专家计算和跨节点专家通信的时间构成 |
| 2 | AFD A0 | 32K 均衡批次 | 没有计算重叠时 Attention、FFN 和 CAM 的实际成本 |
| 3 | AFD A2 | 32K 均衡批次 | 计算重叠是否发生，以及关键路径由哪一侧决定 |

条件性能追踪：只有无插桩结果中 32K 长短混合批次的 A2 比 A1 快至少 10%，
才增加一次 A2 长短混合性能追踪，用于展示 token 均分如何消除阶段失衡。

### 9.3 条件性的强制均衡诊断

正式结果始终使用自然路由。只有满足下面任一条件时，才在 32K 均衡批次上
增加一次强制均衡诊断：

- FFN 设备进程 token 数的变异系数大于 0.25；变异系数等于标准差除以平均值；
- 最忙 FFN 设备进程的 token 数超过平均值的 1.5 倍；
- 多层 FFN 尾部时间明显由少量慢设备进程决定。

强制均衡运行只回答“自然路由失衡贡献了多少”，不得进入精度或正式性能
结论。

### 9.4 需要从性能时间线提取的指标

对每个有效混合专家层和阶段，至少提取：

- Attention 计算时间；
- CAM 分发时间；
- FFN 从接收分发数据到发出合并结果的服务时间；
- CAM 合并时间；
- Attention 等待 FFN 返回的时间；
- Attention 与 FFN 的重叠时间；
- 两侧设备忙碌比例和空闲空泡比例；
- 阶段 0 和阶段 1 的实际 token 数；
- 每个 FFN 设备进程的路由 token 数；
- 峰值显存。

跨节点绝对时钟只能作为辅助。优先使用每个进程内部的持续时间，并通过
模型层、阶段和分发/合并通信的因果顺序对齐，不以未经校准的绝对时间戳
直接计算重叠时间。

### 9.5 阶段比例和扩容决策

在 16A16F 的 A2 稳态区间中，定义：

- `T_attention`：Attention 执行时间，不包含等待 FFN；
- `T_ffn`：FFN 服务时间；
- `T_cam`：不能被隐藏的 CAM 通信时间；
- `T_wait`：Attention 等待返回的时间。

用 `T_attention / T_ffn` 估计需要的 Attention 数量：

```text
估计的 Attention 卡数 ≈ 16 × T_attention / T_ffn
```

该估算假设短区间内扩容近似线性，只用于选择下一个测量点：

| 实测阶段时间比 | 后续动作 |
|---:|---|
| 不超过 1.5 | 16A16F 已接近平衡，仍完成 32 卡等资源实验 |
| 1.5～2.5 | 32A16F 是可能的缩放诊断点 |
| 2.5～3.5 | 周末优先运行 48A16F |
| 大于 3.5 | 先运行 48A16F；是否需要 64A16F 留到结果出来后决定 |

无论性能追踪结果是否理想，都不能跳过 32 卡正式对照；性能追踪的作用是解释
结果并指导 64 卡拓扑，不是提前宣布胜负。

## 10. 阶段二：32 卡资源对等容量实验

### 10.1 比较对象

- 传统：`DP4 × TP8，EP32`；
- AFD：`16 Attention + 16 FFN`，A2 按 token 拆分；
- 两边：完整模型、自然路由、eager、相同共同批上限。

### 10.2 用短工作负载寻找容量区间

使用独立的 128 请求 `screening` 连续窗口，不做大网格扫描。先用 32K 固定
批次的无排队完成速率得到粗略服务吞吐 `S`，初始目标输入速率取两个系统
`S` 中较小值的 50%。这个值只用于减少搜索次数，不进入最终结论。

1. 为初始目标 token/s 生成一份缩放后的 `screening` arrival 计划；
2. 两个系统重放同一计划；若都通过则把目标 token/s 乘以 2；
3. 若初始点任一系统失败，则把目标 token/s 除以 2，先建立共同通过下界；
4. 得到最后一个共同通过点和第一个任一系统失败点后，测试两者的几何中点；
5. 当上下界之比不超过 1.20，或已经完成两次中点细化时停止；
6. 每个系统最多运行 5 个筛选点。

每个目标速率只生成一份计划文件，不能为两个系统分别调整到达时间。筛选窗口
基础输入速率约为 40,633.79 token/s；它只是换算时间膨胀系数的基准，不代表
测试系统容量。

筛选结果只用于选点，不作为正式容量结论。

### 10.3 正式负载点

根据两个系统的筛选结果确定：

1. **低负载点**：约为较低容量估计的 50%，用于比较无明显排队时的服务
   延迟；两个系统各运行一次 `formal_0`。
2. **共同近拐点**：选择两个系统都可能满足 SLO、且尽量接近较低容量的负载；
   每个系统依次运行 `formal_0`、`formal_1`、`formal_2`。
3. **较高容量点**：如果一个系统的容量估计明显更高，该系统运行三次；另一
   系统在同一目标 token/s 下先运行 `formal_0`。若失败，再运行 `formal_1`
   确认；若通过，则补齐另外两个正式窗口，不能用一次结果宣称容量分离。

如果两个系统容量估计相差不超过 5%，不增加单独的较高容量点，改为在共同
近拐点补足稳定性证据。

### 10.4 正式容量判定

一个负载点只有在三个完整重复都满足以下条件时才算正式通过：

- 三个正式窗口各自的 512 条请求全部成功；
- 没有客户端超时；
- 每次运行的 TTFT 第 99 百分位都不超过 10 秒；
- 服务端没有崩溃、重启或设备进程丢失；
- 实际 token 数与请求文件一致；
- 客户端发送偏差满足 6.5 节门槛；
- 运行结束后队列能够排空，没有未完成请求。

正式容量是“已经实测并通过的最高负载”，不对未测区间作精确外插。

| 时间段 | 工作 | 说明 |
|---|---|---|
| 第 0～1 小时 | 节点健康检查，启动第一个系统 | 启动失败最多快速重试一次，避免无限消耗窗口 |
| 第 1～3 小时 | 第一个系统筛选与正式重复 | 使用 32 卡结果估计初始负载，最多 4 个筛选点 |
| 第 3～4 小时 | 停止第一个系统，启动第二个系统 | 保存并校验第一组结果后再释放进程 |
| 第 4～6 小时 | 第二个系统筛选与正式重复 | 重放相同到达计划 |
| 第 6～8 小时 | 补齐共同负载、失败见证或异常重复 | 至少预留约 2 小时缓冲，不默认增加新拓扑 |

系统顺序可以根据启动便利调整，但报告中要记录顺序。若第一个系统耗时超出
计划，应优先保证两个系统都有共同近拐点的三次重复，低负载和额外高负载点
可以删减。

### 11.4 64 卡负载搜索

仍使用 128 请求 `screening` 窗口，但每个系统最多 4 个筛选点。初始目标
token/s 根据 32 卡容量和阶段比例估算，不从零开始宽扫。

正式重复规则与 32 卡相同。64 卡窗口的最低可接受产物是：

- 两个系统在同一个共同近拐点各三次完整重复；
- 每次运行都有完整的每请求数据和运行清单；
- 能计算首 token 延迟和有效输入吞吐；
- 没有性能追踪污染。

### 11.5 条件实验

以下实验都不是默认任务：

- 只有 32 卡性能追踪指向约 32 Attention 卡时，才考虑 32A16F；
- 只有 48A16F 的 Attention 仍明显是瓶颈，且 64 卡结果无法解释时，才在以后
  讨论 64A16F；
- 64 卡性能追踪重放只在正式数据已完成且剩余时间充足时进行；正式结果
  优先级高于额外性能时间线。

## 12. 指标和计算方法

### 12.1 主要指标

**满足服务目标的最大有效输入吞吐** 是核心指标。这里的“容量”定义为：

> 三个正式窗口都满足服务目标时，已经实测通过的最高目标输入 token 到达速率。

每次运行同时计算三个速率，不能混用：

```text
目标输入 token 到达速率
  = 请求文件输入 token 总数 / 缩放后到达计划时长

实际发送 token 速率
  = 实际发出的输入 token 总数 / 第一条与最后一条请求实际发送时间之差

完成吞吐
  = 成功请求的输入 token 总数 / 第一条请求发出到最后一条请求完成的时间
```

系统容量采用第一个数，因为实验控制的是开放环计划负载。只有客户端发送偏差
通过门槛时，第一个数才有效；第二个数用于识别发送端未能跟上计划。第三个数
包含队列排空时间，用于发现运行结束时是否积累了大量未处理工作。报告必须
同时给出目标/实际 RPS、目标/实际发送 token 速率和完成吞吐。

因为正式通过要求零失败，所以通过点上的成功 token 数应等于发出 token 数。
出现失败的运行不进入容量候选。容量报告还应给出“最高正式通过点”和“第一个
已观察到的失败点”，让读者知道搜索分辨率，而不是只给一个看似精确的单值。

### 12.2 延迟指标

每次运行分别报告：

- TTFT 第 50 百分位；
- TTFT 第 90 百分位；
- TTFT 第 95 百分位；
- TTFT 第 99 百分位；
- 最大 TTFT；
- 请求失败数和超时数。

不要只报告平均 TTFT。第 99 百分位按每次运行独立计算，不把三次运行的请求
混合成一个更大的样本后再计算。

### 12.3 吞吐和负载指标

- 实际请求吞吐，单位 requests/s；
- 计划发送偏差的第 50、95、99 百分位和最大值；
- 发出输入 token 速率；
- 成功输入 token 速率；
- 队列是否在运行尾部持续增长；
- 每个 Attention 数据副本实际接收的请求数和输入 token 数；
- 实际运行时间；
- 完成请求数。

### 12.4 机制指标

- A0 到 A2 的无插桩固定批次加速比；
- A1 到 A2 在均衡/长短混合工作负载上的差异；
- Attention/FFN 阶段时间比；
- 无法隐藏的 CAM 时间占比；
- Attention 等待 FFN 的比例；
- FFN 设备进程 token 负载的平均值、最大值和变异系数；
- 两阶段 token 数差异；
- Attention 和 FFN 的忙碌/空泡比例。

## 13. 重复、噪声和结论规则

### 13.1 三组成对到达计划

正式三重复分别使用 `formal_0`、`formal_1`、`formal_2`。它们来自 Mooncake
trace 的三个不重叠区域，具有不同但相近的长度和突发形状。对每个窗口：

- 根据同一个目标 token/s 生成唯一缩放计划；
- 传统部署和 AFD 使用相同请求、顺序和到达时间；
- 结果按窗口名配对比较；
- 不在系统之间重新 shuffle，也不重新生成随机间隔。

这样既覆盖三个真实 trace 片段的流量变化，又避免两个系统看到不同的输入。
三个窗口是工作负载重复，不应描述成独立同分布的随机样本。

### 13.2 汇总方式

每个正式点报告三次运行的：

- 中位数；
- 最小值和最大值；
- 每次运行的原始值；
- 成对的 AFD 相对变化。

对需要比较的吞吐指标，定义运行间相对波动：

```text
运行间相对波动 = (三次最大值 - 三次最小值) / 三次中位数
```

同一个对照点的“观测噪声”取传统部署与 AFD 两个运行间相对波动中的较大值。
报告中的“超过噪声”都指性能差异的绝对值大于该观测噪声。

只有三个窗口级样本时，不给出看似精确但不可靠的统计显著性数值。请求之间
共享队列状态，也不能把 1,536 条请求错误地当成 1,536 个独立系统重复。

### 13.3 什么时候增加到五次重复

仅满足下列任一条件时，在资源允许的情况下对 `formal_0` 和 `formal_1` 各做
一次原样重放：

- 三次吞吐的变异系数超过 3%；
- AFD 与传统部署差异不超过观测噪声的两倍；
- 三次结果对胜负方向不一致；
- 某次运行出现无法解释的长尾，但没有明确判定为无效运行。

这两次是用于判断运行噪声的重复执行，不是两个新的流量窗口。报告必须分别
标注“窗口重复”和“同窗口重跑”，不能把五次运行伪装成五个独立工作负载样本。

### 13.4 结论分级

| 结果 | 建议表述 |
|---|---|
| AFD 的最高正式通过速率至少是传统部署第一个确认失败速率的 1.05 倍 | “观察到明确容量收益”，同时报告通过/失败边界 |
| 两个系统的通过/失败区间重叠，或边界差小于 5% | “没有测得明确容量差异”，不能写成容量相同 |
| 传统部署的最高正式通过速率至少是 AFD 第一个确认失败速率的 1.05 倍 | “观察到明确容量回退”，结合性能追踪解释瓶颈 |

5% 是报告分级阈值，不是修改数据或挑选运行的理由。所有有效重复都必须保留。
这里的“正式失败速率”要求至少两个不同正式窗口在同一目标速率失败；如果是
进程崩溃、OOM 等确定性硬失败，也可以在同一窗口复现一次。单个窗口的一次
失败只能写成“观察到失败”，不能单独支持明确收益或回退结论。

机制结论还必须满足额外证据要求。例如，只有 A2 无插桩结果优于 A0，且性能时间线
显示真实 Attention/FFN 重叠，才能写“流水重叠带来收益”。

## 14. 无效运行和停止条件

### 14.1 无效运行

出现下面任一情况，运行标记为无效，不与有效结果平均：

- 模型、Git 提交、容器或共同批上限与计划不符；
- 数据集 revision、bundle ID、请求文件或基础 arrival 校验值不符；
- 自然路由被意外替换为强制均衡；
- `enable_prefill_mc2` 被意外开启；
- 前缀缓存未按要求关闭；
- 性能追踪或调试日志在无插桩运行中开启；
- 请求数据、顺序或到达计划不匹配；
- 客户端发送偏差超过 6.5 节门槛；
- 预热未完成；
- 服务进程在测量中重启；
- 节点、设备或网络出现明确故障；
- 结果缺少每请求首 token 延迟，无法重新校验。

无效运行必须保留原因和原始文件，不能静默删除后只展示重跑结果。

### 14.2 提前停止宽搜

- 已经找到通过/失败边界且相差不超过 20%：停止增加筛选点；
- 连续两个更高负载都失败：不继续加压；
- AFD A2 相对 A0 不足 5%，且性能时间线未观察到有效计算重叠：取消额外 A1/A2
  工作负载扩展，只保留既定正式对照；
- 自然路由负载均衡正常：不运行强制均衡诊断；
- 64 卡正式结果已经完整：不因剩余时间而随意增加没有假设的新配置。

### 14.3 必须停止并重新评审

- 65,536 和 32,768 两个共同批上限都不能公平运行完整数据集；
- 48A16F 无法正确启动或无法通过基本精度/健康检查；
- 两个系统不能重放相同的到达计划；
- 性能追踪无法区分 Attention、FFN 和等待，导致机制归因没有证据；
- 64 卡节点不在相同互联域，资源对等但通信条件明显不等价。

## 15. 运行数量和资源预算

### 15.1 32 卡长期节点

| 工作 | 预计服务启动数 | 说明 |
|---|---:|---|
| 性能追踪冒烟 | 1 | A2，8K 均衡批次 |
| 无插桩机制实验 | 4 | 传统、A0、A1、A2 各一次启动，启动内运行多个固定批次 |
| 必选性能追踪 | 3 | 传统、A0、A2 的 32K 均衡批次 |
| 条件性能追踪/均衡诊断 | 0～2 | 由结果触发 |
| 32 卡正式容量 | 2 | 传统和 A2 各保持一次正式配置，启动内完成筛选和正式重复 |

32 卡节点可长期使用，因此优先在这里消除工具、数据和启动风险。

### 15.2 64 卡周末窗口

- 硬上限约为 `64 卡 × 8 小时 = 512 卡时`；
- 默认只启动传统 EP64 和 AFD 48A16F 两套正式系统；
- 每个系统最多 4 个短筛选点；
- 共同近拐点共 6 个完整运行，即两个系统各 3 次；
- 每次完整运行使用一个 512 请求正式窗口；
- 如果容量明显分离，再增加最多 5 个完整运行：较优系统 3 次、另一系统
  最多 2 次失败确认；
- 至少保留约 2 小时故障和补跑缓冲。

当时间不足时，删除顺序为：额外性能追踪、额外高负载点、低负载点。不能
删除共同近拐点的成对三重复。

## 17. 最终报告允许和不允许的结论

### 17.1 可以回答

- 在完整 DeepSeek-V3.2、自然路由、eager 和给定共同批上限下，32/64 卡等
  资源部署谁具有更高的 SLO 容量；
- 16A16F 是否因 Attention 资源不足而回退；
- 48A16F 是否修复资源比例并获得收益；
- A2 相对 A0 的流水收益；
- A2 相对 A1 在长短混合请求下的 token 均衡收益；
- 专家通信、自然路由失衡和 CAM 开销在代表批次中的占比。

### 17.2 不能直接外推

- 开启前缀缓存后的收益；
- 解码阶段或长输出生成性能；
- Mooncake 原始用户内容、完整生产流量或其他时间区域；本数据只保留公开
  Conversation trace 三个窗口的到达形状，并使用 WildChat 派生内容；
- 其他模型、其他量化方式或其他硬件；
- 计算图模式或上游双批重叠；
- 80 卡 `64 Attention + 16 FFN` 的表现；
- 旧 10 层强制均衡实验的精确加速比。

若最终 48A16F 仍没有收益，应如实报告“在当前完整模型、工作负载和相同资源
下未观察到收益”，并用性能追踪说明是 Attention、FFN、CAM、专家通信还是
调度造成。负结果本身就是完整性能研究的一部分。
