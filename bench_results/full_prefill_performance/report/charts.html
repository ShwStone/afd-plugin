DeepSeek-V3.2 全模型（61 层 W8A8）Prefill 32 卡实验图表

baseline = DP4xTP8 EP32（两节点各 16 卡）；AFD = 16 Attention + 16 FFN 解耦。 SLO = TTFT p99 ≤ 50s。数据源：00_accept / 01_fixed_batch / 02_profiles_32 / 03_capacity_32 + rank0 合并 trace。 生成：fp_render_report.py

1. 容量曲线：TTFT vs 提供负载（screening 窗口 128 请求 / 1.34M tok）

p99 越过 50s SLO 即 FAIL。baseline 拐点 ≈2600 tok/s，A2 ≈4400 tok/s（1.68×）。注意 baseline@4371(52.3s) 比 @3091(74.4s) 失败更轻——Mooncake 同刻突发的采样噪声，正式窗口裁决。

2. 逐请求 SLO 达成率 vs 负载

p99 判定只看尾部 1%；本图显示整体请求面。A2 在 4371 tok/s 仍有 >98% 请求达标，baseline 在 3091 tok/s 已有 ~1/4 请求超时。

3. Goodput（完成 token/s）vs 提供负载

两者都能“做完”远超拐点的负载（排队而非失败），差别在延迟。A2 峰值 goodput ~5.4k tok/s，baseline ~4.2k；低于理想线 = 窗尾排空时间。

4. TTFT 经验 CDF（共同负载点）

4371 tok/s 下 baseline p50 已高于 A2（24.0 vs 18.1s），尾部更是越线；2185.5 下两系统 p50 接近，A2 尾部明显更薄（40.2 vs 46.8s）。

5. TTFT vs 输入长度 @4371 tok/s

下包络 = 服务时间（随长度增长），上方的点 = 排队抬升。两系统服务时间斜率接近，A2 的排队抬升更小且更均匀。

6. 窗内排队动态（到达时刻 → TTFT）

过载点可见到达越早排队越深（队列单调积压），达标点则平坦。突发簇（同刻多点垂直堆叠）来自 Mooncake 原始到达的零间隔保留。

7. 固定批次完成时间（无排队，钉 DP rank 0）

32K 均衡：A2 7.06s / A1 7.21s / baseline 10.01s → AFD 快 ~30%。A0（无流水）两次在 4 个 burst 内 507015 崩（SP+async 竞态），不可得。A2 的 32K 均衡有 1 个 71.7s 离群 burst（其余 6.9-7.6s），原因待查。

8. 长短混合批次内的个请求公平性（32K long-short）

三系统都把短请求压到和长请求一起等批次尾巴（同步批处理宿命）；AFD 整体低 ~24-30%。token 均分（A2）相对按请求拆分（A1）在此负载无额外收益（9.69 vs 9.72s）。

9. 空载单请求延迟扩展律（验收 §8.2）

63,778 tok：A2 27.9s vs baseline 31.8s（-12%）；32,850：-14%。baseline 另有 4×~52K 并发钉副本验证（4/4 成功，43.9s）。

10. Device 时间构成（rank0 全采集窗口并集，含首尾空泡）

注意：全窗口并集未做逐 step 切片，仅供参考。FFN 的 98%“忙碌”里含大量 dispatch_recv 阻塞等待（op 中位 42ms）——真实等待需看 flow 图。

11. CAM 标记→设备算子的排队延迟（profiled 32K 重放，同钟 FIFO 配对）

attention 侧 dispatch_send 从首个 48.6ms 单调积压到 5.8s（队列失衡）；FFN 侧 recv/send 始终 ~1.5ms——FFN 设备队列恒空，瓶颈在 attention 侧算力。
